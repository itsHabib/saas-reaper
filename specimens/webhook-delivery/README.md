# Webhook delivery golden specimen

This module is SaaS Reaper's second customer-owned specimen: one Go process,
one SQLite file, and no vendor to keep paying for HTTP POSTs, HMAC signatures,
and a retry loop. It registers and disables endpoints, publishes exact JSON
bytes, delivers them asynchronously, retries failures on a finite schedule,
replays an immutable message to one endpoint, and exposes an append-only
attempt audit.

The selection rule is deliberate. Reaper targets capabilities sold like
infrastructure even though the essential mechanism is small enough to own.
An open wire protocol plus official third-party verifier libraries makes that
claim testable instead of rhetorical. Factory templates for webhook delivery
are not part of this specimen; the root factory still accepts only the
`feature-flags` capability.

## Run the proof

From the repository root:

```sh
make setup # install the pinned verifier libraries once
make webhook-demo
make webhook-invariants
# or both, after static checks
make webhook-proof
```

The demo starts the service and three receivers on loopback. The receivers use
the official Standard Webhooks Go, JavaScript, and Python libraries. Each one
accepts a real delivery, then changes one valid Base64 signature character and
proves that the same library rejects the tampered signature. Each receipt also
records the raw body as Base64, so the harness compares literal fixture bytes
rather than equivalent parsed JSON.

The invariant harness independently proves:

- two receiver failures are audited before a successful retry;
- an endpoint disabled before publication receives nothing;
- manual replay uses a new delivery record with the original `webhook-id`;
- pending work and prior attempts survive a process restart on the same SQLite file;
- the management token cannot read attempts and the audit-read token cannot mutate.

Dependency installation happens only in `setup`. Demo and invariant execution
make no registry calls and send delivery traffic only to `127.0.0.1`.

## Wire contract

Every attempt sends the stored payload bytes unchanged with:

```text
webhook-id: msg_...
webhook-timestamp: UNIX_SECONDS
webhook-signature: v1,BASE64_HMAC_SHA256
```

The HMAC key is the decoded 32-byte value presented as `whsec_` plus standard
padded Base64. The signed bytes are exactly:

```text
webhook-id + "." + webhook-timestamp + "." + HTTP body bytes
```

Message IDs are generated by the service and contain no full stop. Every retry
and replay retains the message ID and exact payload while signing with a fresh
wall-clock timestamp. Only 2xx is success. Redirects are not followed, 410
disables the endpoint, and a valid `Retry-After` may postpone a retry up to the
24-hour cap. Configured and delta-seconds delays begin when the response or
transport failure completes; an HTTP-date value remains an absolute due time.

The default schedule is finite and follows the Standard Webhooks example:

```text
immediate, 5s, 5m, 30m, 2h, 5h, 10h, 14h, 20h, 24h
```

`REAPER_WEBHOOK_RETRY_DELAYS` injects a comma-separated schedule for local
proofs. The official verifier fixtures always use real wall time because their
five-minute freshness check is intentionally not bypassed.

## HTTP surface

Management routes require `Authorization: Bearer $REAPER_WEBHOOK_ADMIN_TOKEN`:

```text
POST /v1/endpoints
POST /v1/endpoints/{endpoint}/disable
POST /v1/messages
POST /v1/messages/{message}/replay/{endpoint}
```

Endpoint creation accepts `{"url":"https://consumer.example/webhook"}` and
returns a generated endpoint ID plus its signing secret once. Disable accepts
`{"expectedRevision":1}`. Message publication treats the request body itself
as the immutable JSON payload; it never parses and re-serializes those bytes.
Replay has an empty request body.

The read route requires
`Authorization: Bearer $REAPER_WEBHOOK_READ_TOKEN`:

```text
GET /v1/attempts?messageId=...&endpointId=...&limit=100
```

Attempt rows are newest first. They include the configured management actor,
HTTP or network outcome, signature timestamp, and next due time, but never an
endpoint secret or destination URL. Transport failures are classified and
redacted before the lower-authority audit reader can see them. The actor is
snapshotted on each original or replay delivery, so a replay after a principal
change is attributed to the principal that requested the replay.

## Configuration

The three authority values are required:

```text
REAPER_WEBHOOK_ADMIN_TOKEN
REAPER_WEBHOOK_ADMIN_ACTOR
REAPER_WEBHOOK_READ_TOKEN
```

The tokens must differ. Optional runtime settings are:

| Variable | Default |
| --- | --- |
| `REAPER_WEBHOOK_ADDR` | `:8080` |
| `REAPER_WEBHOOK_DB` | `.reaper/webhooks.db` |
| `REAPER_WEBHOOK_RETRY_DELAYS` | the schedule above |
| `REAPER_WEBHOOK_POLL_INTERVAL` | `250ms` |
| `REAPER_WEBHOOK_REQUEST_TIMEOUT` | `20s` |

## Boundaries

```text
management HTTP ──► delivery policy ──► SQLite authority
                            │
                            ▼
                     polling mechanism
                            │
                            ▼
                    signed HTTP sender

audit-read HTTP ──────────────────────► SQLite authority
```

`internal/delivery` owns validation, exact signing bytes, endpoint selection,
replay identity, and retry transitions. `internal/api` translates strict HTTP
requests and keeps the two bearer authorities separate. `internal/store/sqlite`
owns transactions and the append-only attempt table. `internal/transport/httpdelivery`
owns outbound HTTP only. `internal/worker` owns waiting and lifecycle only. The
composition root is `cmd/reaper-webhooks`.

Delivery is at least once. A receiver can accept a request immediately before
the process loses the corresponding SQLite commit; the pending delivery will
then be sent again. Consumers should use `webhook-id` for idempotency. Disable
prevents new work and queued retries after its transaction commits. The shared
single-worker attempt coordinator makes disable wait for an active send and its
atomic audit transition before committing; it cannot recall a request already
accepted by the receiver. Graceful shutdown cancels outbound I/O, records that
final outcome with a bounded audit context, and waits for the poller before the
SQLite authority closes.

This specimen has one worker and one SQLite authority. The database file is
created and enforced as owner-only (`0600`). Endpoint secrets are stored in
that customer-owned database without application-layer encryption.
The authenticated management principal is trusted to choose destinations;
the sender rejects non-HTTP(S) URLs, credentials, fragments, and redirects,
but it is not a substitute for an outbound SSRF-filtering proxy in an untrusted
multi-tenant control plane. TLS termination, secret rotation, event filtering,
jitter, multi-worker leasing, notifications, and factory generation remain
explicit follow-up work.
